# HexWorld — ТЗ 1.0 для Claude Code

**Дата:** 14.11.2026  
**Статус:** задание на реализацию первой рабочей версии, не описание готового ПО.  
**Цель версии:** прочный, расширяемый фундамент процедурного генератора гексагональной географической карты; первая реализованная физическая ступень — **литосферные плиты и их взаимодействия**.

> **Инструкция исполнителю:** начни реализацию проекта, а не очередного ТЗ. Делай работающий код, тесты, минимальный интерфейс и сохранение данных. Не пытайся в v1.0 реализовать всё из будущего плана: см. `HEXWORLD_PROJECT_CONTEXT.md`.

## 1. Принципы, которые нельзя нарушать

1. **Геология первична, гексы — представление.** Генерируй геологические объекты в физических мировых координатах (км) или независимой опорной сетке; затем семплируй их на игровую hex-сетку. Изменение разрешения отображения не должно менять исходный геологический мир.
2. **Причины вместо декоративного шума.** Плиты — не просто раскрашенные случайные области. У них есть движение и реальные относительно друг друга границы. В будущем эти данные определят горы, вулканы, бассейны и другие формы. Шум допустим для нерегулярности границ, но не вместо структуры.
3. **Модульность и поэтапность.** Каждая ступень отдельно запускается, тестируется, сохраняет результат и передаёт формализованные данные следующей. GUI не входит в ядро.
4. **Воспроизводимость.** Тот же сид + параметры + версия алгоритма + закреплённая среда дают те же данные. Изменения цвета или масштаба отображения не влияют на геологию; параметры будущих стадий не меняют прошлые.
5. **Без искусственных краёв.** Карта — прямоугольное окно в более обширную геологическую модель. Плиты и их границы могут продолжаться за пределами видимой области. Не создавать по краям искусственный океан, рамку плит или замкнутые континенты.
6. **Не привязывать проект к Земле или сфере.** Плоская прямоугольная карта допустима. Форма континентов и физическая причинность важнее геометрии глобуса.

## 3. Настройки и геометрия

- Размер: **100×100** минимум; рабочие пресеты **500×300** и **1000×800**; архитектура допускает большие размеры. Время генерации вторично относительно качества (порядка 10 минут на крупную сложную карту приемлемо).
- Гексы: **flat-top**, для хранения прямоугольной матрицы — **odd-q offset**, для вычислений — **axial/cube**; корректные 6 соседей, расстояния и преобразования обязательны.
- Разделить `world_id`, `simulation_bounds_km` (физическая геологическая область), `viewport_bounds_km` (видимый прямоугольник), `width/height_hex` (дискретизация) и физический масштаб гекса. Пиксельный размер гекса — только параметр рендера.
- Режим по умолчанию — `regional`: геология создаётся за пределами viewport с достаточным буфером, после чего отображается окно. Отдельный `world`-пресет может показывать большую часть модельного мира. Не считать край экрана физической границей плиты.
- Число плит: `auto` или ручное целое значение; дополнительно профили `few / earthlike / fragmented`. В `auto` отталкиваться от **физического охвата мира**, а не напрямую от числа гексов. Не закреплять «12 плит» как универсальную истину; при неразумных параметрах показывать предупреждение. Ручное значение относится к области симуляции; число *видимых* плит может отличаться.
- Сид: непустая строка `0-9A-Za-z`, **регистр значим**. `Ab12` и `ab12` различаются. `SHA-256` от сида; независимые потоки по именам этапов, без `hash()` Python, скрытого глобального RNG и зависимости результата от порядка отрисовки. Версии генератора/PRNG записывать в метаданные.

## 4. Первая ступень: тектоническая основа

**4.1. Области плит.** Генерировать неравные по площади крупные, средние и малые плиты. Возможный подход: взвешенная диаграмма Вороного / рост областей с низкочастотным искажением границ. Алгоритм выбирает Claude Code и кратко обосновывает. **Требование к результату:** каждая плита связна, нет одноклеточных обломков и регулярной сотовой мозаики; протяжённые границы естественно извилисты. Исправления связности не должны уничтожать естественные формы.

**4.2. Поле коры.** Создать крупные связные области `continental` / `oceanic` **независимо от раскраски плит**. Одна плита может содержать оба типа. Не объявлять получившуюся маску готовыми материками или океанами: окончательная береговая линия появится после высот и уровня моря.

**4.3. Плиты и движение.** У каждой плиты сохранять стабильный ID, имя, цвет, площадь, мировые координаты центра, доли типов коры, скорость `(vx, vy)` в мм/год и список соседних плит. Цвет и имя детерминированны и не определяют физические свойства. Вектор скорости — не только стрелка для рисунка, а данные расчёта.

**4.4. Границы.** Строить **граф общих рёбер** гексов разных плит (не путать соседство по вершине с общим ребром). Для каждого участка: две плиты, нормаль и касательная, относительная скорость `v_B − v_A`, нормальная и касательная составляющие, тип границы и интенсивность. Комбинации коры сохранять как данные для будущей субдукции и коллизии. На одной длинной границе возможны разные локальные режимы.

**4.5. Диагностика.** Экспортировать поле близости к границе и приближённые потенциалы `uplift / rifting / subduction / volcanism / seismicity`. Это **сигналы для будущих модулей**, а не заявления о достоверной геофизической симуляции. Не считать любую конвергенцию источником вулканов. На этой версии не симулировать геологическое время.

## 5. Контракт данных и архитектура

Реализовать независимые стадии:

```text
config/seed → world_geometry → plates → crust → motion → boundary_edges
            → tectonic_fields → validate → save/export → hex_viewer
```

Каждая стадия получает явные входы и возвращает типизированный результат. Сохранить возможность пересчитывать `motion → ...` без новой генерации плит; изменение отображения не должно повторять генерацию. Будущие модули получают те же **мировые координаты, физические единицы, ID плит, поля и границы**.

Минимальный формат проекта:
- `config.json` — seed, физический масштаб, режим, размеры, параметры и версии;
- `plates.json` — метаданные плит;
- `fields.npz` — типизированные массивы `plate_id`, `crust_type` и диагностические поля;
- `boundaries` — сериализованный граф граничных рёбер (JSON или бинарный файл с документированным форматом);
- `manifest.json` — версии схемы, координат, единиц измерения и контрольные хэши.

PNG — только изображение, не источник географических данных. Нужны программные функции `generate(config)`, `save/load(project)` и получение слоя/значений для гексов и мировой области. Разделить вычислительное ядро, I/O, CLI и GUI. Не переписывать сохранённые исходные данные при перегенерации только визуализации.

## 6. Технологии и минимальный интерфейс

**Стек, согласованный ранее:** Python 3.12+, NumPy, SciPy; PySide6 для локального GUI; pytest, ruff. Ядро независимо от PySide6. Профилировать скорость/память; ускорители позже допускаются, но не должны быть обязательны. В перспективе должен подключаться отдельный горный движок **PMGE** (его спецификация использует C++20) через файловый/API-адаптер — переписывать PMGE на Python не требуется.

Минимальный GUI: сид, размеры, физический масштаб, количество плит `auto/manual`, профиль; кнопки генерации, открытия и сохранения; перемещение/масштабирование карты; слои «плиты / кора / границы / движение / диагностические поля»; просмотр свойств выбранной плиты. Для карты 1000×800 **не** создавать по отдельному UI-объекту на каждый гекс: рисовать пакетно/тайлами. Генерация не блокирует окно; ошибки и прогресс видимы. CLI должен работать без GUI.

## 7. Проверка готовности

Claude Code обязан сдать **запускаемый проект**, а не демонстрационные скриншоты:

1. Карты `100×100`, `500×300`, `1000×800` генерируются и отображаются, без переполнения памяти; привести фактическое время и объём памяти на тестовой машине.
2. Один сид + конфигурация + версии дают те же массивы и хэши после повтора и загрузки; разные регистры сида дают разные карты; смена масштаба GUI не меняет результат.
3. Каждый гекс относится ровно к одной существующей плите; плиты связны; границы соответствуют смежности; нет массовых одноклеточных артефактов.
4. На искусственных примерах корректно различаются встречное движение, расхождение и боковой сдвиг; нормали и знаки компонент документированы.
5. Область, показанная двумя разными окнами/разрешениями одного и того же `world_id`, согласуется в физических координатах в пределах ошибки дискретизации.
6. Сохранённый проект открывается вместе со слоями и параметрами; изменения поздних стадий не меняют ранние без необходимости.
7. README даёт команды установки и запуска (Windows прежде всего), примеры конфигураций, ограничения и список реально сделанного; тесты выполняются одной командой.
