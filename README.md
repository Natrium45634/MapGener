# HexWorld

Процедурный генератор гексагональной географической карты.
**Версия 1.0 — тектоническая основа:** литосферные плиты, поле типа коры, движение плит,
граф границ и диагностические поля. Материков, высот, моря, рек и климата здесь **ещё нет** —
это следующие версии (см. `docs/HEXWORLD_PROJECT_CONTEXT.md`).

Исходное задание: `docs/HEXWORLD_TZ_1.0_Claude_Code.md`.

## Установка

Нужен Python 3.12 или новее.

### Windows (PowerShell)

```powershell
py -3.12 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e ".[gui,dev]"
```

### Linux / macOS

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e ".[gui,dev]"
```

Ядро и CLI требуют только NumPy и SciPy. `gui` добавляет PySide6, `dev` — pytest и ruff.
Без GUI: `python -m pip install -e .`

## Запуск

```bash
hexworld gui
```

```bash
hexworld generate --seed Ab12 --preset medium -o out/medium --png plates boundaries crust
```

```bash
hexworld generate --config examples/large_1000x800.json -o out/large
```

```bash
hexworld info out/medium --plates
```

```bash
hexworld render out/medium --layer all
```

```bash
hexworld hex out/medium 120 80
```

```bash
hexworld validate out/medium
```

Если команда `hexworld` не найдена, то же самое делает `python -m hexworld ...`.

Тесты — одной командой:

```bash
python -m pytest
```

Нагрузочные тесты на 500×300 и 1000×800 (около 25 с):

```bash
python -m pytest -m slow
```

### Параметры `generate`

| Параметр | Значение |
|---|---|
| `--seed` | строка из `0-9A-Za-z`, регистр значим: `Ab12` и `ab12` — разные миры |
| `--preset` | `small` 100×100, `medium` 500×300, `large` 1000×800 (все `regional`), `world` 1000×800 |
| `--width`, `--height` | размер сетки в гексах |
| `--hex-km` | расстояние между центрами соседних гексов, км (физический масштаб) |
| `--mode` | `regional` — окно в более обширный мир; `world` — окно показывает всю область симуляции |
| `--plates` | `auto` или целое число плит с центрами в области симуляции |
| `--profile` | `few` / `earthlike` / `fragmented` |
| `--origin X Y` | левый верхний угол окна в мировых км |
| `--sim-bounds` | явная область симуляции — закрепляет мир при смене окна и разрешения |
| `--config` | JSON-файл со всеми параметрами, примеры в `examples/` |

## Что реализовано и проверено

- **Координаты.** Плоский мир в км (`+x` восток, `+y` юг). Гексы flat-top, хранение odd-q,
  вычисления в axial/cube. Раздельно: область симуляции, окно, число гексов, размер гекса.
  Пиксельный размер гекса — только параметр отрисовки.
- **Сид и RNG.** SHA-256 от сида и имени этапа → PCG64; у каждого этапа свой поток.
  Версии генератора, алгоритма и PRNG пишутся в `manifest.json`.
- **Плиты.** Аддитивно-взвешенная диаграмма Вороного в искажённых (domain warp) мировых
  координатах; малые плиты вставляются на существующих границах. Связность — по построению.
- **Кора.** Отдельное поле `continental` / `oceanic`, не зависящее от плит; одна плита может
  нести оба типа. Это не маска суши и моря.
- **Движение.** Скорость `(vx, vy)` в мм/год и малое вращение вокруг полюса плиты. Плиты с
  преобладанием океанической коры в среднем быстрее.
- **Границы.** Граф общих рёбер гексов: нормаль, касательная, `v_B − v_A`, нормальная и
  касательная составляющие, тип (сближение / расхождение / сдвиг / спокойная), интенсивность,
  типы коры по обе стороны, подсказка полярности субдукции.
- **Диагностические поля.** Расстояние до границы и потенциалы `uplift`, `rifting`,
  `subduction`, `volcanism`, `seismicity`. Это сигналы для будущих модулей, а не геофизическая
  симуляция.
- **Проверка, сохранение, CLI, GUI.** Формат проекта описан в `docs/DATA_FORMAT.md`.

### Почему такой алгоритм плит

Плита задана **функцией мировых координат**, а не раскраской сетки:
`plate(p) = argmin_i |W(p) − site_i| − weight_i`. Отсюда следуют три свойства, которых требует ТЗ:

1. Геология не зависит от разрешения: любая сетка и любое окно семплируют одну и ту же функцию.
2. У карты нет искусственных краёв: центры плит расставлены и за пределами области симуляции,
   функция определена всюду.
3. Ячейка взвешенной диаграммы звёздна относительно своего центра, то есть связна, а взаимно
   однозначное искажение связность сохраняет. Поэтому не нужен «ремонт», портящий формы.

Рост областей по сетке дал бы более причудливые формы, но привязал бы геологию к разрешению.
Сравнение подходов и лицензии источников — в `docs/RESEARCH.md`.

### Соглашения о знаках на границе

Гексы ребра упорядочены так, что `plate_a < plate_b`.

- нормаль `n` направлена **из A в B**; касательная `t = (−n_y, n_x)`;
- `v_rel = v_B − v_A` в середине ребра;
- `vn = v_rel · n`: `vn < 0` — сближение, `vn > 0` — расхождение;
- `vt = v_rel · t`: `vt > 0` — правый сдвиг, `vt < 0` — левый.

## Ограничения

- Идентичность результата гарантируется для одной и той же среды (ОС, версии Python, NumPy,
  SciPy). Между платформами возможны расхождения в последних битах чисел с плавающей точкой;
  бит-в-бит совпадение на разных ОС не проверялось.
- В режиме `regional` область симуляции выводится из окна и округляется до 1000 км. Заметное
  изменение размера окна может дать другой мир. Чтобы менять окно и разрешение в одном мире,
  задайте `simulation_bounds_km` и число плит явно (в GUI — флажок «Тот же мир»).
- Поздние стадии используют кэш ранних только в пределах одного сеанса (`generate(reuse=...)`)
  или после загрузки проекта для стадий `plates` и `crust`.
- Границы плит плавнее настоящих: нет ступенчатого рисунка «хребет — трансформный разлом».
- Полярность субдукции океан–океан выбирается простым правилом, без возраста коры.
- Диагностические поля строятся по текущей кинематике; геологическое время не моделируется.
- Плоский мир: вращение плит задано относительно точки на плоскости, а не полюса Эйлера.
- Запас гексов за краем окна ограничен 64 (`fields.max_pad_hexes`). При гексах мельче ~14 км
  поля у самого края окна не учитывают границы дальше этого запаса.
- Адаптер PMGE не реализован. Данные для него уже есть: мировые координаты, ID плит, поля,
  граф границ.
